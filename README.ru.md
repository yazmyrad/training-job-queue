# training-job-queue

Надёжная очередь задач с воркерами, которые переживают падения. Сделано в рамках бэкенд-задания Soup.

HTTP API на FastAPI, хранилище на Postgres и N процессов-воркеров. Воркеры атомарно забирают задачи, выполняют их с побочным эффектом не более одного раза (at-most-once) и переживают `kill -9` в любой момент.

> **Вердикт для 100 rps: НЕ ВЫПУСКАТЬ.** Корректность подтверждена, готовность к эксплуатации — нет. Нагрузочный бенчмарк не проводился, пула соединений нет, а часть сценариев «тихих» отказов проверена только изолированно. См. [Вердикт](#вердикт-для-100-rps).

```bash

git clone <repo> && cd training-job-queue

docker compose up --build

```

Поднимаются сервисы:

- **db** — Postgres 16, схема загружается из `src/db/init.sql` при первом запуске

curl localhost:8000/health

## Гарантии

- **Побочный эффект не более одного раза.** Обеспечивается двумя механизмами:

  1. Fence при завершении: `UPDATE ... WHERE id = ? AND worker_id = ? AND attempt = ?` — 0 строк означает, что воркер потерял владение задачей.

  2. `UNIQUE(job_id)` в таблице `side_effects` как страховка.

- **Попытка выполнения не менее одного раза.** Lease, повторный захват и reaper вместе гарантируют, что каждая задача за конечное время придёт в финальное состояние.

- **Ограниченное число повторов.** Условие `attempt < MAX_ATTEMPTS` в запросе захвата; reaper переводит исчерпавшие попытки задачи в `failed`.

- **Часы — только у БД.** Все временные метки берутся из `now()` Postgres, а не с серверов приложения. Это убирает рассинхрон часов между воркерами как класс отказов.

- **Идемпотентный API.** Повторный `POST /jobs` возвращает существующую задачу (`200`), а не создаёт новую.

**Не гарантируется: at-most-once для внешних эффектов.** Наш побочный эффект — строка в БД, как требует задание. Реальный эффект, например отправка письма, требует, чтобы внешний сервис поддерживал ключ идемпотентности. Иначе при повторном выполнении эффект продублируется, даже если наша строка записана один раз.

## Доказательства тестирования

Каждый механизм проверялся изолированно до хаос-тестов. Сырые выводы лежат в `docs/chaos/`.

### B.1 — Цикл захвата

**Доказано:** два воркера захватывают разные задачи; `SKIP LOCKED` не даёт захватить одну задачу дважды. Задачи с истёкшим lease захватываются повторно.

**Вывод:** `b1-proof.txt` — 5 задач, распределение w1: 2, w2: 3; при повторном захвате `attempt` растёт.

### B.2 — Fence при завершении и побочный эффект

**Доказано:** 10 задач → 10 succeeded, 10 эффектов, 0 дублей. Ручная проверка fence: фейковый воркер с устаревшим `attempt` получил `UPDATE 0` и не перехватил задачу у текущего владельца.

**Вывод:** `b2-proof.txt`

### B.3 — Heartbeat

**Доказано:** задача длительностью 25 с (2,5× lease) завершилась, не будучи перехваченной другим воркером. Событий LOST нет, ровно 1 эффект, `attempt = 1`.

**Вывод:** `b3-proof.txt`

### B.4 — Reaper и лимит попыток

**Доказано:** «ядовитая» задача 5 раз роняла воркер, затем перестала захватываться (фильтр `attempt < 5`), после чего reaper перевёл её в `failed` с `last_error = 'max attempts exceeded'`. 0 эффектов. Обычная задача, работавшая параллельно, завершилась успешно.

**Вывод:** `b4-proof.txt`

### Интеграция перед хаосом

**Доказано:** 20 задач, 2 воркера, все четыре инварианта (нет потерь, нет дублей, нет зависших, согласованные финальные состояния).

## Тихие отказы — как проверялся каждый

В задании перечислено шесть сценариев тихих отказов. Для каждого: как он проявился бы, что его предотвращает и как это проверено.

### 1. Двойной захват

*Два воркера захватывают одну задачу, оба выполняют её — два эффекта.*

- **Предотвращает:** атомарный `UPDATE ... WHERE id = (SELECT ... FOR UPDATE SKIP LOCKED)` — между выборкой и обновлением нет окна.

- **Проверено:** B.1 (два воркера → два разных захвата) и хаос (0 дублей на 10 000 задач). На ранних итерациях без `SKIP LOCKED` тест становился нестабильным; это состояние не коммитилось.

### 2. Воркер-зомби после истечения lease

*Воркер A зависает, lease истекает, воркер B захватывает задачу (`attempt + 1`) и завершает её. A просыпается и пытается её завершить.*

- **Предотвращает:** `attempt` работает как fencing-токен. `UPDATE` от A совпадает со старым `attempt` и затрагивает 0 строк.

- **Проверено:** ручной тест B.2 (`UPDATE 0` с устаревшим attempt) и 1 событие LOST в хаос-прогоне 01 — реальный устаревший воркер был отклонён.

- **Честно:** 1 LOST на 85 убийств — мало. Окно выполнения (50 мс) намного меньше интервала убийств (~2 с), поэтому большинство убийств не попадает в середину выполнения. Если поднять `SIMULATED_WORK_SECS` примерно до 0,3 с, fence будет проверяться гораздо сильнее. Для прогона выше этого не делалось.

### 3. Гонка отмены и завершения

*Клиент отменяет задачу в момент, когда воркер её завершает.*

- **Предотвращает:** оба `UPDATE` фильтруют по `state = 'running'`; блокировка строки их упорядочивает. Победитель меняет состояние, проигравший видит 0 строк.

- **Возможные исходы:** cancelled + 0 эффектов или succeeded + 1 эффект. Никогда оба сразу и никогда ни одного.

- **Проверено:** в хаос-прогоне 01 — 384 отменённые задачи без эффектов. 2 из 386 отмен вернули `409` (задача уже завершена), то есть в этих случаях гонку выиграл воркер.

- **Не наблюдалось напрямую:** отмена и завершение, пришедшие ровно на границе коммита, — статистически редкость даже на 10 000 задач.

### 4. Дубль при повторе запроса

*Клиент повторяет `POST` с тем же ключом идемпотентности — создаются две задачи.*

- **Предотвращает:** `UNIQUE(idempotency_key)` + `ON CONFLICT DO NOTHING RETURNING`. При конфликте дополнительный `SELECT` возвращает существующую строку со статусом `200`.

- **Проверено:** хаос-прогон 01 отправил 1 294 параллельных дубля POST. Все вернули `200`, ни одного дубля не создано.

### 5. Уровень изоляции транзакций

*Неверный уровень изоляции позволил бы захвату или завершению увидеть несогласованное состояние.*

- **Предотвращает:** стандартный для Postgres `READ COMMITTED` плюс блокировки строк. `FOR UPDATE SKIP LOCKED` на этом уровне безопасен, а условие `WHERE` у fence перепроверяется по закоммиченному состоянию под блокировкой строки, поэтому потерянное обновление невозможно.

- **Проверено:** обосновано структурой SQL (атомарный захват одним запросом, условный `UPDATE` у fence), а не отдельным тестом. На других уровнях изоляции не проверялось.

### 6. Рассинхрон часов

*Машины по-разному видят время; lease истекают раньше или позже.*

- **Предотвращает:** все метки времени берутся из `now()` Postgres — БД единственный источник времени. Воркеры не вычисляют истечение lease локально.

- **Проверено:** только обоснованием дизайна. Хаос-тест идёт на одной машине и не создаёт реального рассинхрона. Это слепая зона, а не тест.

## Что хаос-тест НЕ ловит

Каждый пункт — сценарий отказа, который хаос-тест пропустил бы.

1. **Рассинхрон часов** — все воркеры используют часы одной машины. Смягчено через `now()` БД, но под нагрузкой не проверялось.

2. **Сетевые разрывы** — всё работает на localhost. Разрыв между воркером и БД, скорее всего, выглядел бы как обрыв соединения → падение воркера → истечение lease → повторный захват, но внедрения сетевых сбоев не было.

3. **Failover / перезапуск Postgres** — один инстанс. Перезапуск БД разом рвёт все соединения воркеров; не моделировался.

4. **Гонка отмены и завершения на уровне долей миллисекунды** — статистически недостижима на 10 000 задач. Корректность держится на аргументе о SQL, а не на наблюдении.

5. **Внешние побочные эффекты** — наш эффект — строка в БД. Реальным внешним эффектам (email, S3, сторонние API) нужны собственные ключи идемпотентности.

6. **Утечки памяти, потоков, соединений** — прогон 173 с выявит грубые утечки, но не тонкие. Утечку соединений в потоке heartbeat, найденную на код-ревью, под высокой нагрузкой удалось бы заметить примерно через 30 минут.

7. **Исчерпание пула соединений** — пула нет. Каждый обработчик и каждый heartbeat открывает новое соединение; при 100 rps стандартный `max_connections` Postgres (100) кончится за секунды.

8. **Переполнение диска / OOM** — не моделировались.

9. **Большое число воркеров** — 8 воркеров нормально; 100 воркеров × 2 соединения = 200, больше стандартных лимитов Postgres.

10. **Устойчивые 100 rps** — см. вердикт ниже.

## Вердикт для 100 rps

**НЕ ВЫПУСКАТЬ.**

Корректность доказана на проверенном масштабе (10 000 задач, 8 воркеров, 85 убийств). Но пережить хаос — не то же самое, что держать 100 rps, а пропускная способность не измерялась. Во время хаос-прогона очередь разбиралась со скоростью ~58 задач/с при 85 убийствах — это нижняя оценка, а не бенчмарк.

### Исправить до запуска на 100 rps

1. **Пул соединений.** Каждый запрос открывает новое соединение с Postgres; при 100 rps один только API будет создавать 100 соединений в секунду. Нужен `psycopg2.pool.ThreadedConnectionPool` (или `asyncpg.Pool`). Это блокер №1 — без него система нежизнеспособна выше примерно 10 rps устойчивой нагрузки.

2. **Нагрузочный бенчмарк.** Прогнать `wrk` / `k6` / `hey` на 100 rps не меньше 60 с и выяснить:

   - p99 задержки API (цель < 100 мс)

   - конкуренцию запроса захвата при `SKIP LOCKED`

   - глубину очереди во времени (разбирается или растёт бесконечно?)

   - нужное число воркеров (при 0,05 с симулированной работы 8 воркеров дают потолок ≈ 160 задач/с; реальная работа медленнее)

3. **Настройка `MAX_ATTEMPTS`.** Сейчас 5 без обоснования. 5 попыток × lease 10 с ≈ 50 с окна повторов — скорее всего, мало для нестабильных внешних зависимостей. Должно настраиваться по типу задачи.

4. **Наблюдаемость.** Логов хватает для отладки, но не для продакшена. Не хватает:

   - структурированных (JSON) логов для агрегации

   - эндпоинта `/metrics`: глубина очереди, скорость захвата, доля успехов, число LOST, число reap, число воркеров

   - алертов (reap > 0 — хороший сигнал о «ядовитой» задаче)

5. **Корректная остановка долгих задач.** Обработчик `SIGTERM` выставляет флаг остановки, который проверяется только между захватами. Воркер с задачей на 30 с игнорирует `docker compose stop`, через стандартные 10 с получает `SIGKILL`, а задача повторно захватывается и выполняется заново. Либо проверять флаг внутри `execute_and_complete`, либо задать таймаут остановки больше самой долгой задачи.

### Что работает хорошо

- **Корректность при отказах надёжна.** Ноль дублей эффектов на 10 000 задачах при 85 принудительных падениях — это работа fence, а не удача.

- **Идемпотентность держится под конкурентной нагрузкой** — 1 294 дубля POST, все корректно дедуплицированы.

- **Дизайн защитим.** Каждый механизм нацелен на конкретный отказ, и для каждого есть доказательство, что он его предотвратил.

«НЕ ВЫПУСКАТЬ» — это про готовность к эксплуатации, а не про корректность.

## Что удивило

**Ограничение UNIQUE ни разу не сработало.** На 10 000 задачах и 85 убийствах fence отловил каждый устаревший воркер до записи эффекта, поэтому `UNIQUE(job_id)` не понадобился. Хорошая новость — fence достаточен, — но это значит, что страховка под хаосом не проверена. Она работает в ручном тесте B.2, но не в живом хаос-тесте.

**Идемпотентность оказалась надёжнее, чем ожидалось.** 1 294 параллельных дубля POST: ноль `201`, ноль ошибок. Я закладывал одну-две ошибки `500` при конкуренции — их не было.

**Код-ревью нашло больше багов, чем любой тест.** Четыре настоящих бага — приоритет операторов в запросе захвата, неинициализированный `empty_polls`, утечка соединений в heartbeat и остатки тестового кода в горячем пути — ни один не проявился в изолированных тестах. Два из них (приоритет и утечка) тихие: ничего не падает, система просто работает чуть неправильно. Тесты доказывают то, что проверяют, и ничего сверх этого.

**Мало событий LOST — 1 на 85 убийств.** Окно выполнения крошечное, поэтому хаос-тест в текущем виде почти не нагружает fence. Это не дыра в корректности, а дыра в тестировании.

## Что всё ещё беспокоит

- **Гонку отмены и завершения ни разу не увидели напрямую** на самой границе коммита. Аргумент о SQL надёжен, но путь «проигравший затрагивает 0 строк» доказан только ручным тестом B.2.

- **Reaper не проверялся под хаосом.** В прогоне 01 — ноль срабатываний; reaper доказан только изолированным скриптом B.4. Хаос-прогон с ~1% «ядовитых» задач проверил бы его под нагрузкой. На вопрос «откуда вы знаете, что reaper работает под нагрузкой?» честный ответ: он проверен изолированно, а не под хаосом.

- **Heartbeat почти не нагружался.** При 50 мс симулированной работы и lease 10 с поток heartbeat почти сразу останавливается для каждой задачи. Тест B.3 на 25 с — единственное доказательство, что он удерживает долгие задачи. Нужно проверить его с реалистичной длительностью задач (5–30 с) под конкурентной нагрузкой.

- **10 000 задач — не доказательство для 100 000.** Некоторые отказы проявляются только на большем масштабе: например, autovacuum таблицы `jobs` во время захватов с `SKIP LOCKED` или исчерпание пула, когда он появится.

- **Тихие отказы по лимиту попыток.** Баг в `execute_and_complete` (скажем, путь возврата в обход fence) проявился бы только как рост `attempt` до `MAX_ATTEMPTS` и финал `failed`. Счётчик `failed_due_to_max_attempts` должен быть полноценной метрикой; сейчас приходится грепать логи.

## Использование ИИ

ИИ-ассистенты использовались на протяжении всей работы как напарники по программированию. Согласно политике задания, честный отчёт:

### Где ИИ помог

- **Обсуждение дизайна** — разбор схемы захвата / lease / fence / идемпотентности и проверка граничных случаев (воркер-зомби, гонка отмены, внешние эффекты).

- **Код-ревью** — построчное ревью `src/worker.py` и `src/routers/jobs.py` нашло четыре бага, перечисленных выше. Каждое исправление проверено повторным запуском соответствующего теста.

- **Заготовки тестовых скриптов** — `b4-reaper-test.sh`, `pre-chaos-integration.sh` и `chaos_harness.py` набросаны с помощью ИИ и затем адаптированы под реальную схему, порты и формат логов. Проверки сверены с описанием дизайна.

- **Отладка** — разбор ошибок FastAPI / psycopg2 / Docker. Одна проблема «curl ничего не показывает» оказалась в разнице между `curl -s` (полная тишина) и `curl -sS` (показывает ошибки).

### Отклонённые предложения

- **async / asyncpg** — отклонено. Воркер — синхронный цикл на psycopg2; async добавил бы сложности без выгоды на этом масштабе.

- **bind mount в docker-compose для горячей перезагрузки** — не закоммичено. Задание требует, чтобы `docker compose up` запускал немодифицированный образ, а dev-монтирование может скрыть баг «забыл скопировать файл в образ». Быструю разработку покрывают воркеры, запущенные на хосте.

- **`init.sql`** — черновик ИИ принят с дополнениями (частичные индексы, колонка `last_error`), проверено через `\d jobs`.

### Что проверено, а что принято на веру

- Каждый SQL-запрос выполнялся на настоящем Postgres и проверялся (`\d`, `EXPLAIN`, живые обновления).

- Каждый скрипт прогонялся целиком; сырой вывод сохранён в `docs/chaos/`.

- Поведение `SKIP LOCKED` проверено наблюдением, что два воркера захватывают разные задачи (B.1).

- Fence проверен тем, что устаревший воркер получил `UPDATE 0` (B.2), и одним событием LOST под хаосом.

- **Не проверено под хаосом:** страховка `UNIQUE(job_id)`. Она работает при ручном срабатывании; хаос-прогон её не задействовал.

### Где ИИ ошибался или вводил в заблуждение

- Первый предложенный `docker-compose.yml` не содержал healthcheck для БД, что привело бы к гонкам запуска API и воркеров. Поймано на второй итерации.

- В первом предложенном `init.sql` не было `UNIQUE(job_id)` в `side_effects`; добавлено только после обсуждения страховки на этапе дизайна.

- Переиспользование `get_jobs(id)` внутри обработчика отмены предлагалось как «DRY» и вызвало `500` (у `JSONResponse` нет `.data`). Исправлено inline-запросом. Вывод: DRY между обработчиками маршрутов часто ошибочен — обработчики являются границами единицы работы.

Решения по дизайну — выбор гарантии, уровень изоляции, нужен ли пул — принимал я. ИИ предлагал варианты и указывал на прецеденты.

## Известные ограничения и дальнейшая работа

1. **Нет пула соединений** — добавить `ThreadedConnectionPool` в `src/db/connection.py`.

2. **Нет нагрузочного бенчмарка** — добавить сценарий `wrk` или `k6` на 100 rps.

3. **Масштабирование reaper** — `UPDATE` reaper (`state = 'running' AND lease_until < now() AND attempt >= MAX`) нормально работает на 10 тыс. задач; на 1 млн+ нужен проверенный частичный индекс по `lease_until WHERE state = 'running'` или пакетный reaping через `SKIP LOCKED`.

4. **Нет хаоса с «ядовитыми» задачами** — добавить ~1% всегда падающих задач и проверить, что reaper срабатывает под хаосом.

5. **Heartbeat почти не нагружался** — проверить с `SIMULATED_WORK_SECS` от 5 до 30 с.

6. **Один Postgres, одна машина** — нет проверок failover, сетевых разрывов и рассинхрона часов.

7. **Нет эндпоинта метрик** — добавить `/metrics` (глубина очереди, скорость захвата, число LOST, число reap, статус воркеров).

8. **Корректная остановка долгих задач** — `SIGTERM` проверяется только между захватами.

9. **`MAX_ATTEMPTS` захардкожен** — должен настраиваться по типу задачи.
